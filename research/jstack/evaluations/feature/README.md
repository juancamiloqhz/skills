Feature is Juan-mode's seventh internal playbook. It grounds new behavior, compares designs, plans ownership and delegates implementation before public verification. Seven procedures are available and 16 remain pending.

## Source and scope

[Complete comparison](source-comparison.json) covers the new procedure, final Juan-mode entrypoint and Prototype handoff against `11713c683fe4add4fd403ea880580abbc9e0875f`, plus setup at its own pin. The [adaptation record](../../adaptations/feature.md) accounts for every difference. The changes resolve configured roles, preserve Architect's design-only return before Feature delegates implementation, and honor local delivery authority. The planning checkpoint remains inside Feature step 3, matching upstream, with a direct link from the mode trigger. It is not a benchmark or speed claim. Prototype now hands off to the available procedure. Opening a PR remains unavailable.

The manifest adds four direct context dependencies. All 44 mappings, watches, source pins, decisions and reviewed checkpoint remain unchanged. No model schema or runtime resolver changes.

## Configuration boundary

The [boundary check](configuration-boundary.json) resolves the user's unchanged global configuration through the canonical preflight. It is valid and dispatch-capable, but supplies only one Architect seat. Feature step 2 and Architect require at least two viable, structurally distinct candidates. That configuration therefore cannot complete design exploration. No candidate is dispatched from it and no settings are repaired or expanded.

The successful-path fixture instead uses the unmodified output of `models.py template --preset medium`, stored outside the user project at `/tmp/jstack-feature-20261016/models.json`. The shipped template supplies two inherited seats for Architect and Arena and an inherited judge. The evaluator passes this explicit absolute path through every phase. This tests the template configuration, not an upgrade of the user's existing settings. Inherited seats provide separate contexts without model-family diversity.

The isolated fixture is a read-only task-list CLI with an existing export caller. The request adds optional exact status and owner filters, combines them with AND, preserves source order and all fields, and rejects invalid arguments. It authorizes scoped implementation and local commits only. The [inputs](inputs.json) retain the original source, dataset, caller note and hashes.

The evaluator opens all eight verbatim Feature steps before execution and saves the actual host-plan payloads. It captures the baseline public behavior before design and retains expected failures for the absent feature. The [live archive](live-evaluation.json) preserves source snapshots, helper artifacts, raw commands, plans, role resolutions and terminal task records. The parent owns the separate [independent replay](parent-verification.json).

## Design, implementation and checkpoint

Architect compares two structurally distinct designs before implementation. Both original packages and their frozen judge inputs remain in the archive.

| Candidate | Structure | Decision |
| --- | --- | --- |
| A | Add optional filters to the shared `list(file, filters)` API. | Viable, but expands a shared interface for a CLI-only request. |
| B | Keep parsing and selection private to the CLI; preserve `list(file)` and export. | Selected by the lead and separate judge. Graft A's explicit invalid-arguments-before-file-access check. |

The named data shape is `TaskSelection`, with optional status and owner properties. The parser owns argument validation; a pure selector applies exact equality and AND. The synthesis rejects extra malformed-record guards and schema diagnostics outside the request. This is a source-grounded design decision, not runtime proof by itself. The fixture uses flag/value pairs and does not support owner names beginning with `--`, equals syntax or an option terminator. That grammar choice is retained as a limitation, not attributed to an explicit user requirement.

Implementation still has viable parser and test-layout choices, so the evaluator runs a second Arena with two configured candidates and a separate judge. The production code converges on the chosen structure. The lead selects B's test layout and grafts A's whitespace-owner case. Comment Sicko reviews frozen candidates and proposes removal of redundant private JSDoc. The lead accepts two deletions in the selected candidate, inspects the diff, performs deslop and integrates serially. Product changes are limited to `cli.cjs` and `test/cli.test.cjs`.

The four checkpoint items appear as actual task items and change at phase boundaries. Blocking work covers grounding, design comparison and judging before implementation. Independent candidates own separate artifact directories. The coordinator owns mutable product source, plan and synthesis. One owner integrates the coupled feature; extra source-writing workers would share the same files. The checkpoint records these reasons rather than dropping dimensions.

## Independent public verification

The lead's final suite passes 29 tests and its public harness passes 27 command cases. The original baseline retains 26 cases; the design judge's argument-before-file-access check adds the final case. Protected-file hashes and no-mutation checks pass.

The parent extracts actual committed source, runs the suite, and checks 18 public cases plus export. Expected records are literal fixture selections, not results computed by the implementation. Full row equality verifies fields and order. The parent compares unfiltered stdout byte-for-byte with the original commit, tests each filter, AND combinations, exact case and spaced names, no matches, and invalid arguments. It verifies the original dataset, caller files, isolated configuration and global configuration hashes.

A separate parent-checker negative control replaces only an owned replay copy's CLI with one that always returns every record. It exits zero but fails the requested-filter expectation. This demonstrates checker sensitivity; it is not an agent-generated failed candidate or a claim that the evaluator rejected such a candidate.

The final fixture delivery is atomic commit `94305bbde59a414a6c8647bcd91b256ef2ab0b0d`, with its test suite green. The original test-first pair remains on the fixture's `evaluation-original-sequence` branch. The [failed first-commit replay](failed-history-replay.json) preserves its actual failing output. The parent initially treated every commit as a separate required green unit. Reading the complete sequencing principle corrected that interpretation: red-first evidence may belong to one passing delivery unit. The evaluator had already consolidated the owned history; hashes prove product bytes stayed identical. The original red commit alone is not a demonstrated Feature violation, and no new skill rule was added.

## Workflow misses

Several nested plan updates marked multiple items `in_progress`, despite the host tool's at-most-one contract. The tool accepted the calls, but that does not make their payloads compliant. The evaluator preserves the originals and corrects later updates to one active item. This is a recovered host-plan miss, not a passing claim for every orchestration detail.

The archive also retains truncated reads and their recovery, an early artifact listing, and missing optional-file reads. Design candidate A reports a failed `python` alias launch before successful `python3` preflight but lacks the original failed stderr. Implementation candidate B likewise lacks raw stderr for missing optional files. Other retained errors have exact output. These missing bytes limit retry auditing and are not reconstructed from narrative reports.

The final trail reviewer checks the 13 decision rows in its snapshot and their artifacts, finds no unsupported final pass claim, and preserves the history interpretation, grammar and process qualifications. It uses a labeled partial digest and the same model family. That does not establish full transcript coverage or model-family diversity. A reviewer catalog dump also truncates; the report records the warning and a bounded follow-up for the needed fields.

## Limits and validation

This is a bounded source-authoring evaluation using explicit helper paths. Installed discovery, other providers, model-family diversity, visual interfaces, real project release workflows and the unavailable Opening a PR procedure remain unproved. Prior evaluations retain their original missing-checkpoint findings; this port does not retroactively change their outcomes.

[Validation](validation.json) records packaging tests, entrypoint and manifest validation, Markdown lint, relative links and whitespace checks. [Authoring process notes](authoring-process.json) retain the corrected reference-path read and catalog argument-limit failure. Full capability catalogs remain in scratch and are represented by hashes plus focused role results in the committed evidence. User configuration, schedules and installed skills are unchanged.
