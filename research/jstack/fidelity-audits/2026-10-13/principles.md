## Result and priority

The standalone packaging satisfies the current user requirement, but the principle bodies do not meet the close-fidelity policy. Every upstream body has been replaced by one paragraph. Several retain the central idea while dropping executable procedures, diagnostic tests, examples, exceptions and dependency calls. Other paragraphs reverse upstream rules. The earlier evaluation's lack of a demonstrated bad scenario is not approval of those changes.

Correct these first:

1. Restore the performance verification dependency and its algorithm. `explain-the-number` drops `benchmark-checklist`, including tuned comparisons, alternating repeated trials, physical-limit arithmetic and mandatory inconclusive verdicts. A qualifier on an unreliable number does not replace that procedure.
2. Restore concrete evidence obligations in `build-the-lever`, `prove-it-works`, and `outcome-oriented-execution`. Tool production and replayable evidence became discretionary; full static and runtime verification became generic combined verification.
3. Restore the constructive type-modeling, domain-model selection, foundational sequencing and context-inline rules. These are substantive omissions, not only shorter wording.
4. Resolve deliberate rule reversals separately from required runtime adaptations. Internal trust, even-census causality, layer/time thresholds, assertion rules and containment guards have changed without an explicit user decision in the evidence reviewed.
5. Account for missing standalone helpers. `show-me-your-work` exists only as a partial bundled adaptation in Figure-it-out; `benchmark-checklist` and `typescript-best-practices` have no repository package or manifest mapping. Do not silently treat removed calls as completed adaptation.

## Material findings and correction scope

### F1. Performance decisions can bypass the pinned benchmark procedure

Priority: high. Disposition: restore the dependency contract; helper package is pending implementation.

`skills/jstack/principle-explain-the-number/SKILL.md:8` retains run count, spread and measured bottleneck guidance, but drops the explicit full-procedure dependency from pinned `pstack/skills/principle-explain-the-number/SKILL.md:13`. The missing `pstack/skills/benchmark-checklist/SKILL.md` at the same pin defines:

- Lines 15-17: write the intended claim, inspect what the measurement script counts and ignores, check machine load and cores, and interleave comparisons if noise cannot be removed.
- Lines 21-27: profile in a separate unreported run; watch the load generator; tune every side to production conditions before choosing; compare observed results with resource and fractional-work limits; count failures and validate output correctness; alternate at least five trials per side and report median/range; use statistics when close; measure the end-to-end path; prove work happened inside the timed region.
- Lines 11 and 33: a requested quick ballpark has a specific one-run exception, still checking errors and actual execution. Adoption choices are never ballparks. A claimed difference with an unknown limiter, an untuned side, or unchecked errors/work must be inconclusive.

The local instruction to “qualify claims” does not preserve the no-winner rule for untuned options. Restore the skill call and expose missing-helper status rather than pretending the paragraph implements the checklist. Package the helper separately when its implementation is authorized. Verify with a deliberately fast no-op benchmark, an untuned-versus-tuned choice, a profiler-contaminated run and a requested one-run ballpark. The first three must not produce a winner; the ballpark must remain labeled and check errors/work. No benchmark was executed in this audit.

Priority: high. Disposition: restore, with actual task authorization controlling commits.
