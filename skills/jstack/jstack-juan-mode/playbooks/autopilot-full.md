### Autopilot-full

**You own the verdicts, never the PRs. One owner runs each PR from build to merge, and nothing merges without your clean swarm verdict.** For "autopilot this queue", "full autopilot", and one-owner-per-PR programs. Orchestrate runs a standing program whose coordinator lands verified work itself and whose workers never merge. Here each PR's owner carries the whole lifecycle through the merge, and the root keeps only verification, countersigns, and audits. This is an internal juan-mode procedure. Reading it for authoring or evaluation does not activate mode or start a program.

1. **Mark the operator's items and honor state-then-wait.** Items the operator names stay with the operator. The operator reviews and clicks, and no owner merges one. When the operator asks for the protocol or the plan to be stated, deliver the statement and stop. Execution starts only on the operator's explicit go. Record the queue, named holds, publication and merge grant, concurrency limit and any audit-schedule authority before dispatch. A planning-only request stops here; a missing dependency or authority blocks its affected action, not independent authorized work.
2. **Spawn one owner per PR with the full lifecycle and an early trail.** Resolve the forge once for the program. GitHub CLI (`gh`) is the default. If `command -v origin` succeeds and Origin can resolve the repository, use `origin pr ...` for PR create, edit, view, watch, and merge operations. Otherwise stay on `gh` and record the fallback. Never require Graphite (`gt`). One logical owner per PR owns build, the first push, a ready PR, self-proof on the real artifact (the **jstack-principle-prove-it-works** principle skill), skeptical Bugbot triage per `../references/bugbot-triage.md`, a slop-strip (the **jstack-deslop** skill), `/jstack-no-comments` (the **jstack-no-comments** skill), a rebase onto current trunk, the babysit loop to green (`playbooks/babysit.md`), and the merge itself. Within about 15 minutes, every owner starts a `decisions.tsv` trail per the **jstack-show-me-your-work** skill, pushes its first branch snapshot, and opens the PR ready by default. Honor an explicit draft or local-only request; report that it limits this delivery contract rather than overriding it. Publication still requires the operator's grant. After that, the owner pushes its branch again after every verifiable unit (hooks on, a WIP commit is fine). Open the PR before self-proof so the URL, decisions, and checks form a durable trail. Keep `decisions.tsv` uncommitted and return it with the reports. As soon as a subagent starts, the owner adds its ID, expected runtime (at least the longest past run of that kind), and state to a `children.tsv` kept the same way. The owner does the first rebase before the code-ready report and babysit, whether or not trunk has drifted. In fix rounds, the owner keeps that merge base. The owner rebases again only at merge prep (step 5), on a `git merge-tree` conflict with trunk, or on a CI failure that comes from a change on trunk. When the shipped code is final, after the slop-strip and `/jstack-no-comments`, it reports the code-ready head SHA. It also reports the SHA of each later push that changes the patch. Self-proof, CI, and babysit then run in parallel with the swarm. The owner reports merge-ready with the head SHA when self-proof, CI, and babysit finish. Before a push that starts a round, run the pre-review checks that the repo's AGENTS.md files and rules name for the touched paths. Run them on the committed head. A hook pass is not proof. To publish each rebase, push the owner's own branch with `git push --force-with-lease` after an `ls-remote` check. Never force-push a shared branch. The merge is the one step an owner may not take alone. Step 4 gates it. Discover and read the actual helper packages and [Opening a PR](opening-a-pr.md); missing proof or required review remains incomplete. Resolve each owner's implementation role and hardest-task override through mode preflight, retaining the selected absolute configuration and model/effort. Use T3 `delegate_task` with `isolation: "worktree"` for separate checkouts, based on the parent local commit; verify the assigned base and do not assume uncommitted parent edits were copied. A worktree is not a cloud VM. Retain task IDs, worktree/branch ownership and the publication deadline. Keep the logical owner across fresh delegated rounds with the complete brief, findings and artifact pointers; a new review round always gets a fresh task. Do not use a top-level conversation or send a new delegated review through its backing child thread. The root links every PR and owns `watch_pull_request`; owners return the current head and blockers instead of polling or registering watches. The root routes wakes to the owner, rechecks task state plus pending child runs, and prevents duplicate writers. Keep local trails recoverable under the repository retention policy; missing helper audit/review is not a clean handoff.
3. **Run owners in true parallel and never stack.** Many owners at once when PRs are self-contained: one writer per branch, disjoint files, cross-PR drift absorbed by rebase. Only genuinely overlapping work serializes. Respect the observed host capacity and the recorded in-flight limit; independence does not justify an unlimited fan-out. Self-contained PRs branch straight off main, and sequenced work is merge-then-branch. One exception: an owner that must split a genuinely dependent change may hold a short private base-branch stack.
4. **Swarm-verify every round before its merge.** A round starts at the owner's code-ready head SHA and at each later push that changes the PR's patch. At that SHA, fan out parallel independent verifiers per the **jstack-swarm** skill and aggregate to one verdict. The merge needs a clean verdict from the round whose patch matches the merge-ready head. Audit the receipts in the merge-ready report before the verdict. The lanes: re-run the gates at that SHA. Prove the load-bearing behavior live on the real surface the change touches (with the matching control skill, such as **jstack-control-cli** or **jstack-control-ui**, or a named driver where none exists). Audit the diff, distrusting the PR body. Run the audit as two or more review lanes with the full brief. Give each lane one main focus, such as consumer parity with trunk, lifetimes and races, or data and config safety. **Regression lane against trunk.** Run the same load-bearing scenario on current trunk. If trunk does not have the feature, record that fact and gate the behavior the diff adds plus the end state the user waits for instead of pretending trunk can produce it. The live lane is the floor, and a verdict without it is not clean. No merge without the root's clean verdict. When the lanes return, send every proven finding against the PR to the owner in one fix-forward. A defect that a lane filed as a note is a finding. For each behavior finding, ask for a red test that covers every site with the same defect. Where no test can show the defect, ask for a repro receipt instead. Add that defect to the next round's review brief. The new head gets a fresh swarm and a fresh verdict, except for lane results that stay valid under the patch-id rule in [Shipping](shipping.md). Resolve `swarm workers` through the configured Swarm contract. Give every independent lane the full brief, exact base/head, scope and evidence location; the owner cannot verify its own work. Retain all lane receipts and inspect their commands, results and gaps, not just a PASS label. An errored, missing or untested required lane leaves the verdict incomplete. Use Shipping's patch-identity and lane-reuse rules here, not its root-owned landing sequence; this procedure keeps merges with owners.
5. **On a clean verdict the owner merges, and a fresh owner takes the next item.** The owner merges only from a head freshly rebased onto trunk. Merge prep never comes before a round's lanes start, and it ends with a rebase onto current trunk right before the merge. After the merge-prep rebase, the owner reports the new head SHA. CI must pass on that head before the merge, and the patch-id rule decides whether the round's verdict still holds. Once that head is green and its patch-id matches the verdict's under the patch-id rule in `playbooks/shipping.md`, a later trunk move does not force another rebase. Right before the merge, fetch trunk and check that `git merge-tree` of the head against current trunk is clean. Also check that no path in `git diff --name-only $(git merge-base HEAD origin/main) origin/main` is a path the PR changes or a path that decides which CI runs for it, such as the repo's CI config paths. If either check fails, rebase again, report the new head SHA, wait for CI to pass on it, and repeat these checks. A new head voids the verdict unless the patch-id is unchanged. The owner squash-merges its own PR through the resolved forge and returns. A fresh owner picks up the next self-contained item from the queue, per juan-mode's Subagents section. The operator's full-autonomy grant plus the root's clean verdict is the merge authorization that babysitting alone never has. Operator-named items stop at merge-ready and wait for the operator's click. Record the grant and root verdict for the exact candidate before dispatching merge work. Honor repository merge policy and an explicit user-selected method; squash remains the default. Use an expected-head guard where the forge supports it and confirm the actual merged state and commit afterward. An unknown forge result stays unresolved; reconcile it before retrying or dispatching another item.
6. **Run the root layer.** A genuinely new raise of a pinned gate or budget value (a limit CI only lets tighten) needs your fresh countersign, granted only after verifier proof. If the operator's grant or standing orders cover approvals, that countersign is the approval. The owner records it in the form that the tool's approval contract allows, with a pointer to the root's countersign. A lane checks the record against that countersign. The root never gives or bypasses an approval that the forge enforces. Absorbing values that already landed on main is drift, not a raise. Run an audit tick over all owners every hour. The hourly tick needs a supported, explicitly authorized recurring mechanism. If the operator requests that cadence, use a scoped T3 schedule bound to this coordinator, retain its ID/next run and teardown policy, and have each trigger reconcile the same program before acting. A general go or full-autonomy grant alone does not authorize a persistent schedule. Without one, report hourly coverage unavailable, audit at active-turn and supported event boundaries, and preserve a checkpoint rather than claiming unattended coverage. Native goals also need an explicit goal request. Do not substitute shell polling, a hidden timer or a new top-level conversation. At each tick, re-read the current canonical jstack procedure, for example `git show origin/main:skills/jstack/jstack-juan-mode/playbooks/autopilot-full.md` in the jstack source checkout. In a consuming project, use the discovered canonical package source, not that project's unrelated `origin/main`; if it cannot be refreshed, retain its identity and report freshness unverified. Audit the operation against the inspected procedure. Fix drift during that tick. Probe each owner with a generic liveness or status check, and collect the decision trails. Count only side effects as progress: commits, pushes, PR or check deltas, and store reports. Treat a lane that errors, or that passes its expected runtime without a side effect, as stuck. Request cancellation promptly and inspect terminal status and pending child runs. Replace needed work without waiting for a polite report, but establish that the old writer stopped or isolate the replacement on a distinct checkout/branch and reject late writes before giving it write authority. The tick judges an owner by the pushed branch and the decision trail that step 2 requires, and it replaces an owner whose agent cannot start a turn. Each tick also runs the lane stuck test over the program's agent list, where the platform has one, and over every owner's `children.tsv`. Whether or not a stop works, the root has the owner record each stuck subagent as stuck and, if its work is still needed, replace it under that same stop-or-isolate rule. Unknown task state is not evidence of cancellation. Each replacement that stalls gets the same steps. The root takes both steps when the owner cannot. A stall never proves or drops the work. When merges batch, run a retro pass and a post-merge bot-comment sweep. Use the discovered **jstack-reflect** skill for the retro, retaining its proposal/application boundary; external replies require communication authority. Drain or checkpoint every delegated item, even after the last merge. A tick with pending work remains incomplete and continues on supported events; do not busy-wait or declare the program finished from one completed child turn. End the program only when the queue and required follow-ups are reconciled. Unwatch owned PRs on handoff and stop only this program's recurring audit when its recorded teardown authority permits.
7. **Stand down instantly on the operator's stop.** The operator's hold or stand-down reaches every owner as a zero-writes order immediately. Owners hold their briefs until the operator releases them. Follow [Pause safely](pause-safely.md): cancel owned tasks, confirm terminal state with no pending children, reconcile any in-flight writes, unwatch owned PRs and change the audit schedule only when the stop covers it. Record unresolved writers; no new dispatch or merge follows a hold. A message requesting zero writes is not proof that writing stopped.

**Reply:** the queue with each PR's owner, state, and head SHA. Each verdict and the swarm that produced it. What merged and what each fresh owner took next. Countersigns granted and why. Open operator gates. Where the collected decision trails live. Include pending task/watch/schedule IDs, unverified lanes, cadence or restart gaps, and the next authorized action. Distinguish proposed actions from confirmed publication and merges.
