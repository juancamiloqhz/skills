### Hillclimb

**You own the metric and the experiment's integrity. Supervise and review. Delegate the attempts.** For sustained, iterative improvement of one measurable thing against a target. A one-off fix is Bug fix or Perf issue. This is the loop.

Core discipline: one change, one measurement, keep or revert. Never stack untested changes, and never claim a win from code inspection (the **jstack-principle-prove-it-works** principle skill).

1. Ground the workload and architecture before choosing the metric. Run the **jstack-how** skill over the target, name the realistic workload dimensions that can move the result (data size, history, state, concurrency), and select a case that reproduces the user's complaint. If no case reproduces it, fix the repro instead of hillclimbing. Then fix one metric, the direction that counts as better, and a checkable stop predicate that pairs a target with a floor on attempts so a lucky early win can't end the run (the example "at least 50% better than baseline and at least 10 iterations" is this shape). Use the user's numbers when given, otherwise agree them. Discover the helpers and pass their configured roles, source scope and selected absolute configuration through the mode's preflight.
2. Build the measurement harness, prove its sensitivity, then freeze it (the **jstack-principle-build-the-lever** principle skill). Run contrasting realistic workloads and confirm the target case reproduces the symptom while easier cases separate as expected. If the harness cannot distinguish them, revise the workload or metric. Vet the harness with the **jstack-benchmark-checklist** skill before you freeze it, and make it print its error count and a count of the work done. Once frozen, one repeatable command emits the metric, sampled enough to clear the noise (median of N, not a single run). Record the baseline metric and a green run of the regression gate (the tests that must keep passing) before any change.
3. Open the decision log via the **jstack-show-me-your-work** skill. Keep one canonical `decision.tsv` using that helper's format, one row per attempt. Put the attempt id and change in the decision, the hypothesis in why, and tests and verdict (kept or reverted) in result. Point evidence to the attempt's before, after, delta and note. This preserves the experiment fields without a competing log schema. Read it before each attempt. Keep it out of git in task-owned scratch or an already ignored location; do not change ignore settings automatically. Follow the helper's append-only audit and configured independent review.
4. Ground each hypothesis in the architecture model from step 1, so it names a specific mechanism ("defer X off the boot path because it blocks first paint"), not "try memoizing something". For a perf metric, order hypotheses by the performance mantras in step 2 of the Perf issue playbook (`playbooks/perf-issue.md`). Borrow only their order, not that step's stop rule.
5. Loop, one hypothesis per iteration:
   - Hand the change to a subagent using the configured `hillclimb` role, or `hardest tasks` when warranted by the mode's difficulty rule, with a tight scope. Resolve through the mode's preflight and retain the selected absolute configuration; no fixed-model fallback. Supervise and review the diff rather than typing it (the **jstack-principle-guard-the-context-window** principle skill). When several independent hypotheses are live, fan them to parallel subagents, each in its own worktree (the **jstack-principle-separate-before-serializing-shared-state** principle skill). Use T3 Code worktree isolation when separate checkouts are needed and inspect the assigned base and actual artifacts; uncommitted parent edits are not copied.
   - Measure before and after with the frozen harness, and run the regression gate.
   - Accept only when the metric moves past noise and the gate stays green. Otherwise revert the attempt's change in full, preserving unrelated work. A tweak that "might help" is not kept.
   - One commit per accepted fix, staging only the files you changed (`git add <files>`, never `-A`). Commit only within the task's authority; for uncommitted local delivery retain the verified changes and proposed commit order. Log the row either way, kept or reverted.
   Each iteration ends in a check before the next begins (the **jstack-principle-sequence-verifiable-units** principle skill). If the run is unattended, borrow only the wake mechanism from the Autonomous run playbook (`playbooks/autonomous-run.md`), not its stop rule. That procedure remains unavailable in this package. Unattended continuation needs an actual supported wake mechanism within existing authority; do not invent a wake, create a schedule or claim the unavailable procedure ran.
6. Push past the first plateau. On a stall, several rejects in a row, pivot category, combine near-misses, re-read the source, or try something more radical before concluding the hill is climbed. Correctness and simplicity outrank the number. Revert a win that breaks behavior, and keep a simplification that holds the number (the **jstack-principle-laziness-protocol** principle skill).
7. Stop when the predicate is met, or when the remaining ideas are marginal and not worth their cost. Don't relax the predicate to meet it, and don't quit while cheap untried hypotheses remain. If you are stuck, surface it instead of spinning. Preserve explicit user checkpoints and run limits. If stopping before the predicate is met, say so and report the remaining gap.
8. Run **Opening a PR** with the accepted commits stacked in the order they landed when publication is authorized. Read and follow [Opening a PR](opening-a-pr.md). Preserve local-only delivery. This playbook does not authorize merging or installation.

**Reply:** the metric and target, baseline to final with the percent delta, iterations run (kept vs reverted), each accepted fix on one line, the `decision.tsv` path, and the best idea you would try next if pushed further.
