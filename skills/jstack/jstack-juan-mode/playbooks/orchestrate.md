### Orchestrate

Reading this procedure does not activate juan-mode or authorize a program. Check the selected runtime, provider capabilities and task authority before starting.

**You own the program, never the code. Author briefs, drain the queue, keep the frontier green, decide.** For a whole project handed to one standing coordinator chat: multi-day, many stacked PRs, dozens to hundreds of subagents, the human checking in twice a day instead of every five minutes. One task driven to a predicate is Autonomous run. One ambitious run needing a bespoke workflow is figure-it-out. Route here when the work outlives any single agent. Work one agent could finish inside the session's budget is not a program.

Ceremony must scale with the program. On cheap near-identical units, collapse it as each section directs.

Three rules carry the rest.

- Completions are queue events, not interrupts.
- Every spawn and every resume carries the standing orders verbatim.
- The brief is the product. A vague brief fails quietly, because a child may pause on missing context and cannot assume the parent is waiting to answer.

#### Roles and placement

- **Coordinator (this chat).** Local. Frames, authors briefs, drains the inbox, owns the human report, makes judgment calls. It never authors or edits code. Conflicted merges, restacks, and code changes are always tasks. Mechanically landing a verified unit (fast-forward or clean cherry-pick of a worker's commit, then push) is bookkeeping the coordinator may do itself on repos where local git is cheap. Queueing finished work behind an idle stacker is how a deadline harvests nothing. The loop is agentic end to end. Agents are dispatched and reconciled through supported native or T3 Code child tools under [the execution contract](../references/execution.md). Use a fresh child with consolidated context for each new round. The parent owns PR links and watches; child results and supported PR events wake the coordinator. State reads and writes go through `scripts/orch/orch.ts` at drain points, one command in and one line out. The CLI never spawns, waits, or wakes anything.
- **Sub-coordinator.** One durable logical role per track, and only when the program exceeds what one coordinator's drains can manage. A track the coordinator can drain itself needs no middle layer. Each nested layer re-pays a full orientation preamble, and a blocking sub-coordinator hides its children while the parent idles. Owns its track's units and boards, authors its workers' briefs, and spawns its own workers and verifiers only when the observed host supports nested child work. A logical role survives fresh agent rounds through its saved brief and records; do not assume a child conversation or process is durable. Rolls up aggregates at wave boundaries. Never forwards raw child reports. Cap in-flight children at the lower of observed host capacity and what one drain can process, roughly ten, as a rolling window. Record the actual cap and reserve coordinator capacity. Never as blocking batches, which cost the slowest child of every batch.
- **Worker / verifier.** Place work through supported T3 Code delegation, with `isolation: "worktree"` when a separate checkout is needed; there is no assumed Cursor cloud environment. Read the actual child checkout/base and preserve one writer per worktree or branch through the **jstack-principle-separate-before-serializing-shared-state** skill. Keep machine-bound UI/CLI verification, local transcripts, simulators, IDE state and local-only authentication where those resources are available. A child may not see the parent's store, so inline its inputs or provide verified accessible paths. Prefer fewer, broader workers. A dedicated verifier uses a different model family from its worker. Resolve task-specific implementation roles, `judgment and prose` for delegated coordination, and `swarm workers` for verification through the mode's configuration preflight. Preserve saved selections; an unavailable or same-family verifier is an unmet gate, not permission to substitute models.

Depth stays at coordinator, track, worker, within the host's observed nesting limit. Author the track decomposition per project (build, landing, and verification are common cuts, not a required shape). Hard-coded swarm trees were tried and parked as too rigid.

#### Store layout

Choose an explicitly recorded durable store path ending in `orchestrate/<project-slug>/`. T3 does not supply Cursor's store path. Use one host for this store because its PID lock is not a distributed lock. Do not bypass a live holder with `--force`. Every file has exactly one writer. Owners publish facts, readers aggregate at read time. Resolve this package's absolute `scripts/orch/orch.ts` and use `bun <resolved-orch.ts> --store <absolute-store>` for bookkeeping, written below as `orch`, while its canonical plain TSV and JSON stay readable without the CLI.

- `preferences.md` is the standing-orders register: numbered lines, one constraint each (model policy, stack shape and count, verification bar, forbidden paths, escalation policy). Paste it verbatim into every spawn and every resume. Directives decay across resumes, and each dropped one costs a human turn. When you catch yourself restating an instruction, append the line before you act (the **jstack-principle-encode-lessons-in-structure** skill).
- `overview.md` is the durable PR and issue DB. Append. Never rewrite wholesale per event.
- `units.tsv` has one row per unit: id, track, state, branch, PR, head SHA, brief path. Update rows in place.
- `frontier.json` is the computed merge frontier, per Stack safety.
- `ledger.tsv` is the verification ledger, per Verification.
- `inbox/` holds completion pointers. `gates.md` parks human gates (question, options, default on no answer).
- `decisions.tsv` is the trail via the **jstack-show-me-your-work** skill.
- `status.md` is derived from `units.tsv` and `ledger.tsv` at each drain, never hand-maintained. Regenerate it from the tables instead of narrating events into it.

#### The brief

Your prompts to agents are your only product, and a sloppy brief compounds into slop across the whole tree. Every spawn carries all of it. A field you cannot fill is a unit you have not scoped yet.

```
GOAL         one sentence, the outcome, executable by a stranger with no chat access
SCOPE        paths this unit may write; paths it may not; its exclusive worktree or branch
CONTEXT      pointers to files and PRs; upstream reports pasted in full when this unit
             depends on them, because workers cannot see siblings
ACCEPTANCE   checkable criteria, one per line
VERIFY       exact commands or the control-skill path, plus known gotchas
TIMEBOX      rough cap on runtime; on expiry, return partial findings and stop rather than run on
FORBIDDEN    no gt, no rebase, no force-push, no fixes outside scope, plus unit-specific bans
REPORT       status, branch, head SHA, PRs, verdict, what you actually ran, deviations,
             suggested follow-ups
STANDING     <preferences.md pasted verbatim>
```

Size the brief to the unit. A one-command unit gets the template collapsed to a paragraph that still names goal, scope, the verify command, and the report shape. A 4KB scaffold around a two-line edit costs more to write and obey than the edit. Local spawns may reference the standing-orders file by store path. Verbatim paste is for children without verified store access and every fresh continuation. T3 delegation carries no parent history.

A sub-coordinator brief adds its track boundary and unit list, its spawn budget with observed host capacity and placement requirements, the drain protocol, and the rollup format (per child: name, status, PR, head SHA, verdict, one line, plus track status and frontier delta).

A dependency is a context relay, not just ordering. Undeclared upstream context makes the worker guess. Missing fields are a refuse-to-spawn condition. Audit one sampled worker brief per sub-coordinator per wave, concurrently with the wave it samples, never as a gate in front of it. A failing brief stops that track and fixes the sub-coordinator's instructions, not just the worker, because brief quality decays late in a run. Never resume-chain a brief. Respawn fresh with consolidated scope.

#### Steps

1. **Frame.** State the done predicate as something countable ("all 126 units merged, each ledger-verified `unit-test-verified` or better"). Quantify scope: units, rough effort, expected stacks, and the wall-clock budget. If one agent could finish inside that budget, stop here and run Autonomous run instead. Collapsing must not depend on another document being present. It means do the work directly in this session, plain workers where they help, verification inline, landing as you go, and none of the store, register, or pilot machinery below. Schedule landing against the budget. By roughly 70% of it, stop spawning and land what is verified. Name the tracks per project. A contested decomposition or one-way door goes through the **jstack-arena** skill before the pilot. Present the framing once. Reversible prep proceeds without waiting.
2. **Install the runtime.** Check the bundled runtime prerequisites, then run `orch init`. The helper never installs dependencies; missing prerequisites require manual setup from this package's scripts directory with `bun install --frozen-lockfile`. Report the blocked step and continue independent preparation. Open the trail via the **jstack-show-me-your-work** skill, write the standing orders before any spawn, and seed `frontier.json` from the explicitly owned ordered PR chain with `orch frontier set --repo <repo-dir> --prs <bottom-to-top-numbers>`. With no published PRs, retain the initial empty frontier and record that no landing is eligible yet. The implemented reader supports same-repository GitHub chains; unsupported forge or fork topology is a gap, not guessed evidence.
3. **Pilot.** Push one unit through the whole path: brief, worker, verification, stack entry, ledger row, merge. The pilot exists to falsify the brief template, the verify recipe, and the unit size while that costs one agent instead of fifty. Fix the contract from pilot evidence before any fan-out. A missing prerequisite or absent landing authorization leaves the pilot incomplete; do not call a local simulation or an unmerged unit a completed pilot. Continue independent framing and brief preparation while that gate remains open. Scale the pilot to the unit. On programs of near-identical cheap units, the first unit is the pilot, run as a normal unit with its verify command inline, and fan-out starts the moment it lands. The dedicated pilot pipeline (separate verifier agent, audit gate) is for expensive or novel unit shapes, not for clone-units where a serialized pilot has nothing to falsify.
4. **Scale.** Spawn a rolling window of workers up to the in-flight cap, refilling as children finish. Blocking batches pay the slowest child of every batch. Spawn track sub-coordinators only past the one-drain threshold in Roles. Recompute ready work after each drain. Relay upstream reports into downstream briefs. Keep sibling communication upward only. The sampled brief audit runs alongside the wave it samples and stops the next refill on failure, not the current one.
5. **Drain.** Run the queue discipline below at every drain point and the [completion reconciliation contract](../references/execution.md#completion-reconciliation-with-orch) before accepting results.
6. **Land.** Landing is continuous, never a terminal phase. Land only under the user's applicable merge/push authority and named holds. Integration starts with the first verified unit and runs alongside the remaining waves. On heavy repos the stacker is a standing role from wave one, integrating as units verify. On repos where local git is cheap, the coordinator lands verified units itself per Roles. Keep the frontier green before upper-stack work. Stack safety governs. Advance `frontier.json` only on merge or reported new head SHAs.
7. **Close.** Drain the final inbox, reconcile every spawned agent to a terminal row (done, abandoned, zombie-reconciled), confirm the predicate on the real artifact, confirm every landed PR has a verdict for its current head SHA, audit the trail per the **jstack-show-me-your-work** skill including its cross-model review, encode recurring corrections into `preferences.md` or the brief template. Leave the store intact. It is the postmortem. Unwatch owned PRs at handoff and stop an owned recurring schedule only under its recorded teardown authority. Missing audit evidence, provider recovery or a current-head verdict remains explicit; completion counts cannot hide those gaps.

#### Queue and drain

- On a completion notification, run `orch inbox push <task-id> <unit> <status> [--report PATH]` and return to what you were doing. Never deep-review inline. A completion that needs review becomes a verifier unit. Never review a diff inside a drain.
- Drain in batches at four points: the end of a critical section, a track rollup, a parent-owned PR watcher wake, and before a human report. Begin each batch with `orch inbox claim --json`. Use the claimed batch and completion reconciliation contract to save every classification and applied row change, render status, then `orch inbox ack <batch> --receipt <path>`. Recover an existing claim before claiming another. The destructive legacy drain is not the resumable path. Arrivals during a drain wait for the next one. A persistent heartbeat requires explicit recurring-work authorization, recorded cadence/ownership and teardown. Without it use supported completion and PR wakes, disclose the cadence gap, and never claim unattended heartbeat coverage.
- Critical sections you finish first: authoring a brief, a stack operation, a conflict decision, writing a gate, updating ledger or frontier.
- Each drain classifies every pointer (landed, needs-verify, failed, zombie, noise), writes the resulting rows through `orch unit add`, `orch unit set`, and `orch ledger record`, runs `orch status`, then spawns the next wave in one message.
- Account for every spawned child at its track's rollup: arrived, respawned, or its scope explicitly absorbed. Silently redoing a missing child's work hides both the wasted spend and the coverage gap its result existed to close.
- A drain turn ends with the three lines from `orch status`: counts against the states, what changed, gates open. Detail lives in `status.md`. The full reply contract applies at checkpoints and close.

#### Stack safety

- The frontier is a computed object, never narrative. Recompute `frontier.json` after every merge and stack mutation with `orch frontier set --repo <repo-dir> --prs <bottom-to-top-numbers>`. Record each stack's explicit scope; one frontier file represents one chain, so retain distinct store scopes for independent chains and aggregate their status. The reader checks published GitHub refs, bases and ancestry and rejects moving or unsupported topology. Re-read state before acting; repeated reads are not an atomic forge snapshot. A failed refresh preserves the old record but does not make it current.
- Exactly one stacker per stack may change topology, serialized within its stack. Record the holder in standing orders. Use a T3-bound worktree for isolated stack work; do not assume cloud execution. The stacker records old parent/base/head, quiesces affected writers, and uses explicit Git/forge operations with expected-ref leases under the [Autopilot-stack topology mechanics](autopilot-stack.md). Import only its steps 6 and 7 topology and re-verification rules, not its owner loop or route-specific landing ban. Orchestrate's landing authority still governs. Never require Graphite (`gt`).
- Workers never rebase or mutate topology. Babysitters follow [Babysit](babysit.md), one per stack, scoped to one immutable frontier generation. They report conflicts to the stacker rather than restacking. The parent links worked PRs and owns their supported watch; children return evidence instead of watching.
- PR closes and retargets go through the stacker only, with applicable authority. Closing a base PR orphans every chain above it. Merges and stack surgery are units with briefs like any other. Check the current verdict and frontier before each authorized landing. Apply this procedure's verification bar and the user's named gates; a green PR alone is insufficient.
- One logical retro watcher follows merged PRs for reverts, post-merge CI breaks, and orphaned follow-ups. Record the available parent-owned events and any separately authorized cadence; if post-merge events are unavailable, report the coverage gap instead of claiming an active watcher.

#### Verification

Scale verification to the unit. When VERIFY is a single cheap command, the worker runs it and reports the output, and the coordinator spot-checks receipts. A dedicated verifier agent (on a different model family than the worker) is for units whose verification is expensive, judgment-laden, or high-blast-radius. A verifier agent whose entire product would be rerunning one command is ceremony, not verification.

Write ledger rows with `orch ledger record`. Check the current PR and head SHA with `orch ledger check`. `ledger.tsv`, one row per verdict, keyed by PR number plus head SHA: `live-ui-verified | unit-test-verified | type-check-only | verifier-blocked | verifier-failed`. CI green is an input to a verdict, not a verdict. Behavioral work needs better than `type-check-only`. `verifier-blocked` is not a pass. Respawn when the environment heals. `verifier-failed` gets a fix unit, not a re-verify. A worker may self-report. A verifier overrides it on the same key. Recover the role from its recorded dispatch and preserve verifier precedence when processing later worker notices. Read the actual JSON verdict; an exit-zero ledger lookup only establishes that a row exists. A new head SHA voids the row, so re-verify after restack. The ledger answers "was this verified", not memory and not the transcript.

A unit is not done until its output is externalized the moment it lands, never batched to the end of the run. A worker pushes its branch, a verifier writes its ledger row, receipts land in the store. Work that exists only on one VM when that VM dies was never done.

#### Liveness and failure

- Never resume an agent to check on it. A resume restarts an idle agent. Probe read-only: the ledger, `units.tsv`, `gh`, pushed branches, read-only `task_status` and supported native child status. A completed turn with pending children or a pending question is not a completed task. The runtime may start a later reporting or recovery turn without a new parent dispatch; inspect pending runs and actual writers before assigning its scope elsewhere. Transcript mtime is not liveness.
- A silent death gets a synthetic postmortem row in the inbox (unit, failure mode, last evidence, options). Replan on evidence as it arrives. Never wait for program-wide quiescence. Before replacing a writable scope, confirm that its previous writer has stopped and reconcile its changes, or isolate the replacement and reject late writes.
- Retry by mode: cap-hit or oom, respawn with smaller scope. Network-drop, retry as-is. Tool-error, retry on a different model only when the saved selection or an explicit user decision permits it; otherwise report the selection gate. Unknown, retry once. Two retries, then abandon the unit and replan around it.
- A zombie that returns hours late reconciles against the current frontier and ledger before anything is accepted. Salvage unique findings through a fresh unit, never a blind merge.
- When continued spawning would produce garbage tree-wide (bad upstream output, broken acceptance, dead infra), write a stop line at the top of the standing orders, let in-flight work finish, fix the cause, clear it.
- Bound your own infra retries the same way you bound a child's. After a few consecutive tool aborts, stop retrying. Write a terminal handoff to durable state (what is done, where it lives, the exact command to resume) and end the run.
- After a host restart: read standing orders, units, original task/run bindings and replacement records; recover the pending inbox claim and saved classification receipts; refresh each affected frontier; query supported child status and actual branch/PR artifacts. Do not assume all local children died or all remote work survived. Resume each needed role through a fresh task with its stored brief, current state and standing orders, only after ownership reconciliation. Apply [completion reconciliation](../references/execution.md#completion-reconciliation-with-orch) before replaying row changes or accepting late results. Use [Session pickup](session-pickup.md) for missing evidence and [Pause safely](pause-safely.md) for an explicit hold. If the old task cannot be observed or stopped, record the gap and preserve or isolate its scope. A dead same-host store PID lock clears on the next write; that proves nothing about child/provider survival.

#### Escalation

Reaches the human, batched into the status page rather than per item: irreversible actions (force-push to shared branches, deploys, deletions, closing someone else's PR), genuine product or preference calls no experiment settles, a standing order that contradicts observed reality, a program-level dead end that survived a replan. Park each as a `gates.md` entry before asking, and route work around it.

Within existing authority and observed capabilities, these do not need repeated permission: frontier nudges, restack mechanics, retries, CI flake triage, review-thread triage, format fixes, scope the brief already forbids (refuse and continue), and "should I keep going". Proceed with reversible authorized work and log it. A gate default is a proposal, not approval; elapsed time does not answer a required user decision. A stop or pause halts new dispatch and landing while owned work is reconciled.

Mid-run discoveries fix only what blocks the frontier. Everything else parks in follow-ups. At this fan-out a small scope leak multiplies into PRs nobody asked for.

**Reply:** at checkpoints and close: the predicate and the count against it from `units.tsv` and `ledger.tsv`, tracks and what each landed, the frontier (PR list plus SHAs), verdicts summary, what was abandoned and why, gates awaiting the human (the only asks), the store path, and the trail path. Numbers from the tables, not narrative. Include PR links. Distinguish live evidence, local simulations, incomplete pilot/recovery checks and unresolved child ownership.
