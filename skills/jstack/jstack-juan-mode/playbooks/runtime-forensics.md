### Runtime forensics

**You own the diagnosis. Instrument the live process, don't theorize from source.** The deliverable is a cited diagnosis, not a fix.

1. Capture the live signal on the matching surface via the control skill: a CPU profile for a spinning process, a heap snapshot for a leak, a CDP trace for a visual glitch. A real artifact, not a guess. Discover and read the matching control skill, including `jstack-control-cli` for terminal applications; terminal or browser driving alone does not establish profiler access. Missing runtime access or tools leaves the affected step incomplete, without authorizing installation.
2. Reduce the artifact to the smoking gun: the function on the hot path, the retainer chain from the leaked object to a GC root, the loop firing without input. Parse large artifacts in a subagent (the **jstack-principle-guard-the-context-window** principle skill), keep the reduced finding in the main thread. Use configured `judgment and prose` for delegated reduction, or `hardest tasks` when the causal analysis warrants it, retaining the selected absolute configuration and bounded artifact scope.
3. Prove the mechanism before believing it. Inject instrumentation via CDP eval on the running process, or hotfix the live code without reloading, to confirm the hypothesis cheaply. Use only authorized temporary instrumentation on an identified instance, preserve source files, and restore changed runtime state and remove owned probes afterward. If that intervention is unavailable or outside scope, report the supported hypothesis and missing proof rather than a confirmed mechanism. Retain the actual commands, observations and artifact paths; a controlled fixture does not establish a production performance improvement.
4. Map the finding back to source: file, symbol, the line that allocates or schedules. Missing symbols remain an explicit attribution gap.
5. Throughput checkpoint stays one line: `throughput checkpoint: n/a, read-only forensics`. Here read-only means diagnosis without a source fix; temporary runtime changes still require the scope and cleanup in step 3. Stop and reap only processes this run owns, preserving requested evidence and unrelated sessions.

**Reply:** the signal captured, the reduced finding, how you proved the mechanism, the source location, artifact paths. No fix unless asked. Hand back to Bug fix or Perf once the cause is known. Preserve existing implementation authority, but disclose that Perf issue remains unavailable; diagnosis alone does not authorize a fix.
