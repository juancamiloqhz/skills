### Shipping

**You own what lands. Verify each PR independently, land only the verified run from the root, then keep your hands off the stack.**

This is the half after [Babysit](babysit.md). Run it only for an explicit request to merge, land, ship or merge when ready. A verification-only request stops before publication or merge. Skill invocation does not grant additional authority.

1. **Resolve the forge, then verify each PR independently before it lands.** GitHub CLI (`gh`) is the default. If `command -v origin` succeeds and Origin can resolve the repository, use `origin pr` for every PR operation. Otherwise stay on `gh` and record the fallback. Never require Graphite (`gt`). One verifier per PR, each in a separate T3-bound worktree through `delegate_task` with `isolation: "worktree"`, each exercising the real surface with the matching discovered jstack control skill, such as `jstack-control-ui` or `jstack-control-cli`, against parent versus head. This is checkout isolation, not a cloud VM. Resolve `swarm workers` with this mode's configured preflight and a fresh catalog. Pass the selected absolute model-config path, exact PR base/head revisions, task scope, control-skill path and owned output location. Preserve the configured model and effort. These verification children are read-only reviewers of the product, not code-writing delegates. Give each a fresh context; it must not be the agent that wrote the code. Missing dependencies, failed dispatch or untested lanes are verification gaps, never passing verdicts. Each returns `PASS`, `PASS+NOTES` or `FAIL` with commands, observations, gaps and patch identity. The parent checks the evidence and posts the verdict on that PR only when PR-comment publication is authorized; otherwise return the proposed verdict locally. The parent owns all PR linking and watches. Safe means a verdict from an agent that did not write the code. CI green is not a verdict, and an approving bot review is not a verdict.
2. **Land only the contiguous verified run rooted at the bottom.** Walk up from the lowest unmerged PR and stop at the first one without `PASS` or `PASS+NOTES`. The PRs below it are the run, and the top one is the ceiling. A verified PR above an unverified one waits, because it cannot land without the code below it. One whose branch neither holds nor needs that code can move onto trunk and land on its own. It needs a fresh verdict first, because its old one ran with that code beneath it and trunk does not have it. Establish that independence from the resulting diff and runtime behavior, not just a conflict-free cherry-pick. Complete any extraction before starting the landing pass; keep it outside the original frozen run.
3. **Re-check that the verdicts still describe the code.** A verdict covers a patch, and a chain rebase moves every PR above it to a new SHA without failing any check. Record the verdict base/head as full commit IDs and retain their original diff. Compare `git diff <actual-base-sha> <head-sha> | git patch-id --stable` for the verdict and current PR, using each actual PR base rather than an assumed trunk or merge base. A missing, failed or empty patch-id result is unverified. Never reconstruct old evidence from moved branch names. When the patches differ only in tests, docs, or lint config, a lane's result stands if what it ran builds the same at both SHAs apart from noise. Build it twice at the verdict SHA and once at the current head. Noise is a difference that also shows up between two builds of the verdict SHA, or an embedded commit SHA. Report each kind of noise with its files, so a reader can check the call. The change itself still gets fresh checks and a review, because the old verdict never saw it. A lane with no build output, such as a dev server, cannot show this, so rerun it, and re-verify anything else that drifted. An unchanged patch can retain its code verdict, but mergeability and CI must pass at the current head. A reused verdict or lane receipt remains under its original identity. Callers with PR/head ledgers record a current-head assessment citing that evidence and fresh checks; they never relabel an old row.
4. **Land bottom-up, one PR at a time.** Inspect status, ownership and the frozen bottom-to-top PR list before mutation, preserving unrelated work. Record each child's old parent tip before any parent rewrite and retain that cut point until moving the child. Fetch current trunk and prepare only the lowest PR on its exact tip when needed; confirm the actual forge base is trunk and reassess step 3 before landing. Honor the user's merge authority, named holds and repository merge method. Preserve shared-history constraints and publish rewritten branches only within existing authority. Always merge the run's lowest unmerged PR, with `origin pr merge <pr>` or `gh pr merge <pr> --squash`. Squash is the GitHub default unless repository policy or the user selects another method. Guard the verified head where supported, such as `gh pr merge --match-head-commit <head-sha>`. On Origin the plain command also merges every PR below the one you name, and on GitHub a PR whose base is still its parent's branch merges into that branch, not trunk. Read the PR back for the result (`origin pr view <pr>` or `gh pr view <pr> --json state,mergedAt,baseRefName,headRefOid,mergeCommit`), because a merge command can report success when a merge queue only queued the PR, and a requested auto-merge is not a merge. A landed PR reads merged with trunk as its base, not its parent's branch. Fetch trunk and confirm the forge's actual merge commit is present; a squash need not preserve the PR head. Unknown, queued or mismatched base/head/merge evidence does not advance the run. Arm `--auto` (Origin merge-when-ready or GitHub auto-merge) only when the user requested merge-when-ready and the PR's verdict covers its current head, because it lands whatever head is ready. After a confirmed merge, move only its immediate child within the frozen run. Before retargeting or rewriting, confirm affected writers are quiescent and the recorded cut point belongs to the child history; missing or ambiguous ancestry stops the move. Retarget that PR to trunk (`origin pr edit <pr> --base <trunk>` or `gh pr edit <pr> --base <trunk>`), move only its own patch onto the confirmed merge result with `git rebase --onto <merge-result> <recorded-old-parent-tip> <child-branch>`, and push the owned branch with an explicit expected-ref `--force-with-lease`. Use an available built-in PR tool for retargeting per [Opening a PR](opening-a-pr.md). Re-read the actual remote head/base after each mutation, then rerun step 3 and current-head checks. Do not move higher descendants yet. The verdict covers the patch, not its commits, so step 3's patch-id rule decides whether the verdict survives. Merge it once its checks pass and its verdict survives.
5. **Leave the stack alone while it lands.** Step 4's move of the next PR is the only change to a branch or base, because a merge lands whatever its branch and base hold at that moment, verdict or not. In T3 Code, the parent owns PR links, watches and wakes. Read the current active-forge state and head/base identity; the bundled GitHub queued watcher is a single-pass assessment, not an event source or merge proof. For a pending authorized merge, call `watch_pull_request` for the current bottom PR and end the turn. On a host wake, re-read the forge and patch identity and continue only after step 4 confirms the merge. Do not run `/loop`, a shell watcher or a sleep/poll loop. Babysit's merge-ready or queued `WAITING`/`merge-queue` result is not Shipping completion. Query errors leave an incomplete assessment. If the forge cannot be watched or the host does not resume, save the frozen run, ceiling, current PR/base/head, verdict identities, merge/arming evidence and next read in a recoverable checkpoint; do not promise unattended progression. A base that moves to trunk when its parent merges is expected, not damage to repair. If a merge stalls, find out why before you change anything.
6. **Stop at the ceiling.** Extending the run takes new verdicts, so it is a new pass through step 1. Before handing control back, unwatch scoped PRs, reconcile `list_thread_pull_requests` and link any missing worked PR. Keep unresolved evidence and owned worktrees recoverable; cleanup and installation are separate actions.

**Reply:** the verified run and its ceiling, each PR's verdict and who produced it, what landed and how you confirmed it, and what the next gap needs.
