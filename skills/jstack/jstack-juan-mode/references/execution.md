# Execution contract

Use the current tool schemas and injected T3 Code instructions. Prefer native same-provider children when they support the resolved model, options and required lifecycle. Use T3 Code `delegate_task` for cross-provider work, selections the native tool cannot express, or explicitly T3 Code-owned children. Catalog presence and preflight success are prerequisites, not proof a provider ran successfully.

## Child brief and lifecycle

Supply the following in every child brief because T3 Code delegation does not copy the parent conversation:

- Original goal, later constraints, relevant findings and selected procedure.
- For ordinary playbook children, the discovered absolute mode path with an explicit full-read requirement and applicable principle leaves; specialized workflow children keep their own briefs.
- Absolute checkout path, base revision, owned paths and read-only or write scope.
- The parent's selected absolute model-config path, passed explicitly to preflight in the child.
- Permitted commands or actions where the task needs a narrow boundary.
- Output location, observable acceptance checks and the evidence to return.
- Review findings and unresolved objections when this is a new review round.
- Stop condition and actions reserved for the parent.

For T3 Code dispatch, choose a distinct `clientRequestId` per logical round and reuse it only when retrying that dispatch. Retain the returned `taskId`; `childThreadId` is backing storage, not a target for continuing review. Every new task, follow-up, fix, retry or queue item uses a fresh child and consolidated brief by default. A non-review continuation requires named expensive live state that cannot reasonably move; a running child may receive stop/hold instructions without becoming a new work round. Each T3 review round always uses a fresh `delegate_task` with the consolidated brief. Use completion delivery and `task_status` when needed mid-task. A wait timeout does not cancel work, and a completed turn with pending child runs is not task completion.

Before replacing or abandoning a task, cancel its owned child work and reconcile any writes. Never give the same writable scope to a replacement while the original can still write. Inspect actual artifacts and verification output before accepting a child summary. Record task ID, effective selection, checkout, revision, permitted scope, outcome and evidence in the task's existing handoff when the work needs recovery.

## Completion reconciliation with orch

When using the bundled `orch` helper for resumable completion processing, apply this protocol. It supplies the result-acceptance boundary for the planned Orchestrate procedure; it does not activate that unavailable route. Keep decisions in the program's existing overview, briefs and classification receipts, rather than introducing a second task database. The CLI records facts supplied by the coordinator; it does not authenticate them or enforce these acceptance rules.

1. **Bind the work.** Before accepting results, recover the dispatch record: unit, worker or verifier role, current attempt, `taskId`, original `childRunId` when available, owned checkout/branch and expected artifact. Record replacements explicitly, including which older attempt they supersede. Names, a child thread ID or a unit ID alone cannot establish which attempt owns the work. If the binding is missing or ambiguous, retain the result as unresolved and recover evidence before changing the unit or ledger.
2. **Read the actual result.** Enqueue a notification using its task ID, then use `orch inbox claim --json` to retain the batch. Read `task_status` for every distinct task represented. Match its task/run identity to the dispatch record. Accept a successful completion for assessment only when the original task is `completed`, `workState` is `result_available`, and no pending child runs or pending question remain. Failed, cancelled or interrupted tasks require their failure classification; running, waiting, missing or unreadable status remains unresolved. `waitTimedOut` is not cancellation. Keep later `latestTerminal*` results separate from the original `childRunId` and `summary`; they are not a replacement result for the original dispatch. If required fields or the result are unavailable, inspect supported read-only task evidence or report the gap.
3. **Reconcile repeats and replacements.** Check previous classification receipts by task ID and original run ID, retaining a result reference or report digest. A repeated unchanged result is a duplicate pointer, not another completed unit or another ledger write. Conflicting contents for the same identity need investigation. A superseded attempt is stale even if its summary says success. Salvage unique findings through a fresh scoped task after ownership is reconciled; do not apply its changes blindly. Native children need equivalent recorded identity and liveness evidence, not invented T3 fields.
4. **Check the current artifact.** Read the actual branch and PR state and compare the reported PR/head with the unit and fresh frontier evidence. Refresh an affected frontier through its explicit PR scope. A result for an older head cannot verify the current one. Keep old evidence under its original key; do not relabel it with a new SHA. A worker's new output needs artifact inspection and the unit's verification gate before acceptance. A missing branch, moving head or unresolved writer blocks that acceptance.
5. **Preserve verifier precedence.** Establish the report's role from the dispatch record, not from its prose or a caller-supplied verifier label. Read the existing ledger entry and its provenance before recording a verdict for the same PR/head. A worker report cannot replace an independent verifier's verdict, including failed or blocked verdicts. A later verifier round may supersede an earlier verdict only with its own recorded assignment and current evidence. The latest arrival is not necessarily the latest authorized round. A new head needs new verification; CI green and an exit-zero lookup are not a passing verdict.
6. **Record before acknowledging.** Classify every pointer, including duplicates, stale attempts, failures and unresolved tasks. Save each decision with its task/run identity, original reported PR/head, current artifact evidence, and the unit/ledger changes actually applied. On replay, compare those saved changes with current rows and finish only the missing work. Re-render status, save a durable classification receipt, then acknowledge the exact claimed batch with `orch inbox ack <batch> --receipt <path>`. An unresolved result may be acknowledged only after its blocker, evidence and concrete next action are durably recorded. A receipt's existence alone does not prove these steps happened.
7. **Resume from observed state.** After interruption, read standing orders, dispatch/replacement records, the pending batch and previous decisions. Recheck task status and artifacts before accepting or replacing work. A stable terminal result does not prove later child runs have stopped. Confirm quiescence and reconcile writes before reassigning a writable scope. End with current unit counts and unresolved items; duplicate notices and stale successes must not inflate progress.

## Workspaces

A child that needs a separate checkout uses T3 Code `delegate_task` with `isolation: "worktree"`, across any provider or model. It starts from the parent's local commit and completes project setup before the child runs; uncommitted edits are not copied. Ensure the intended base and required inputs are committed or provided as explicit read-only artifacts before dispatch. Do not simulate app binding by asking a child to create or change to a worktree in its prompt. Do not create a commit merely to dispatch if committing is outside the task's scope.

Retain the returned task identity and inspect the actual assigned checkout, branch, base revision, edits and verification before accepting the result. Keep shared plan files parent-owned and ports, logs and mutable build outputs separate. Separate checkouts do not by themselves prove every provider/editor's behavior. When a separate checkout is unnecessary, a shared checkout is valid for bounded reads or serial writes; concurrent writers require disjoint ownership and demonstrated tool behavior.

Parallel read-only work can proceed within its scope. Independent top-level conversations use `t3_thread_launch` only when the user requests them, with an explicit workspace strategy. Creating a top-level conversation is not a workaround for child isolation.

## PRs and verification

The parent links every worked PR with T3 Code. The parent also owns PR watches and wake handling; children return results instead of watching. Read existing comments before watching, dispatch fresh work for new findings, and stop watching when handing responsibility back to the user. Check readiness against the current PR head and forge state before any authorized merge.

Keep task delivery separate from mode activation. An implementation request does not itself authorize merging, publishing unrelated messages, installing skills or recurring schedules. Use already-granted authority without repeated confirmation. Preserve local user work and report incomplete verification accurately.
