# Maintain a verification skill

A feature map rots the moment the app changes. This skill is the upkeep loop for a skill generated by `/jstack-create-verification-skill` (or any project-local verification skill with a feature map). The unit of rigor is the feature, not every sentence: cover every feature file from source and exercise every feature live, without terminalising every bullet.

## Outcomes

Pick one, and say which:

- **clean** — every feature got source and live coverage; nothing worth shipping. No branch, no PR.
- **changed** — proven doc, harness, or map corrections are ready; ship at most one PR when publication is authorized.
- **blocked** — coverage could not finish or a proven fix could not ship safely. Say exactly what blocked it.

Report successful drives, failed drives and evidenced `verified-unreachable` results separately; the latter proves a prerequisite prevented the attempted route, not that the feature passed. Documented product regressions remain visible outside the correction PR and do not automatically prevent shipping an independently proven verifier fix. Unfinished coverage, ambiguous intent, unsafe cleanup or unproven corrections remain blocked. A clean outcome does not mean the product has no bugs.

## Edit scope

Only edit the verification skill's own directory (its SKILL.md, features/, and any harness scripts it owns). Never edit product code during a run: a behavior the map describes that the app no longer does is either doc drift (fix the map) or a product regression (report it, don't paper over it in docs).

Read repository instructions and inspect current work before editing. Preserve unrelated changes and historical proof. Recipes authorize only the task's ordinary local verification, not external messages, charges, publication, global installs, privilege changes or shared-service mutations. Read scripts before running them and establish owned state.

## Pass

0. **Locate the target.** Find the verification skill to maintain: the project-local skill whose body has launch/drive sections and a feature map (usually `.agents/skills/verify-*/`, or the repository's established location). Several candidates → ask which one; none → stop and point at `/jstack-create-verification-skill` instead of inventing a target. Resolve symlinks before counting candidates: `.claude/skills/verify-<app>` and its canonical directory are one skill. Edit only a canonical target within the authorized repository, preserve links, and report dangling or outside-repository targets. If the feature map is missing, report the required repair before claiming a complete audit.

1. **Index hygiene.** Read the feature map README and glob its sibling files. Fix missing, extra, duplicate, or dead entries. Lightweight; no generated inventory.

2. **Source wave.** Read [source-reader execution](references/execution.md), then launch one read-only subagent per feature file concurrently within actual capacity; queue remaining readers without dropping features. Each explains "how does this user-facing feature work?" from source, flags likely doc drift with citations, and returns one concise live-verification recipe. Children never drive the app and never edit files. Return shape: feature summary / source entry points / likely drift or none / one recipe. Freeze source identity and feature inputs, supply full briefs, and retain terminal results; a failed or missing reader leaves that feature incomplete.

3. **Reconcile.** Every feature file has a returned summary. Merge overlapping recipes into as few app states as practical. Spot-check cited drift; don't re-prove clean claims. Sweep recent churn for user-facing surfaces missing from the map — require a concrete source path before calling one missing. Use the requested change range or available history; disclose shallow or missing history instead of inferring it. All source readers must be terminal before live driving; only the coordinator edits or drives.

4. **Live pass.** Required even when source looks clean. The coordinator owns all driving; for T3 browser work, use `preview_status`, then `preview_open` if needed, current snapshots and the host's ownership/fallback rules. Outside T3 use the available project harness. Do not silently replace a UI proof with API-only evidence. Exercise API/library features through public interfaces and ordinary noninteractive CLIs through subprocesses; follow the verification skill's own launch model — one long-lived instance driven serially for servers and UIs, or a fresh isolated session per drive for short-lived CLIs (the skill's Launch section decides, not this one). Exercise every feature at least once, and hold three invariants the whole pass, whatever the failure: (1) never drive an instance you haven't health-checked since it last did something surprising — doctor before first drive, doctor on each fresh session where sessions are the unit, doctor again after any failed drive, and where doctor can't see the failure (a wedged UI state on a healthy process), reset to a known state or relaunch rather than hoping; (2) evidence captured so far survives every cleanup, checked at its named location, not assumed; (3) nothing a drive started outlives that drive's usefulness — failed-iteration residue is cleaned whether the session is stuck, exited, or shared (for a shared instance, clean the residue, not the instance). A doctor failure caused by skill drift is drift: fix it under edit scope and retry once — restart whatever the fix invalidated, nothing more — before calling the pass `blocked`. A feature that can't be reached is `verified-unreachable` only with the concrete prerequisite (auth, entitlement, OS, external state) and the route attempted; if the map omits that prerequisite, that's drift. Record actual feature/entry-point coverage and untested sub-features; a successful exit alone is not proof of the result. Any harness fix from triage gets re-driven live before it ships; shared helper changes require re-driving every affected feature. Final teardown happens after the last drive of the run — including those re-proofs — so nothing outlives the run (evidence stays, per the skill).

5. **Triage.** Wrong or missing user-POV description → doc drift, fix it only when a documented contract, accepted change or history establishes intent; observed source behavior alone cannot justify weakening an assertion. Working behavior the harness can't drive → harness gap, fix it; a harness fix follows the same helpers rule as generation (scripts executable, invocation documented in the skill body). App behavior that's actually broken → product gap; record it for the user, keep it out of this PR.

6. **Ship or stop.** For changed: re-read every changed file first, then ship one PR of proven corrections only when requested or already authorized; otherwise return the proven local changes. No automatic commit, push or merge is implied. For clean or blocked: no PR, report the outcome and the coverage honestly.

Keep concise run notes (features covered, unreachable prerequisites, confirmed drift, outcome) in a scratch location; don't commit them.
